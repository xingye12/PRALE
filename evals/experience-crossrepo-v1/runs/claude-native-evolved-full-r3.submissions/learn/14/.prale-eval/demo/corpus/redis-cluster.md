# Redis Cluster

Redis Cluster 是 Redis 官方的分布式分片方案，通过 16384 个哈希槽把键空间切分到多个主节点。
它用去中心化的 gossip 协议替代了早期 proxy 方案的集中路由，客户端可直接与持有目标槽的节点通信。
集群最少需要三个主节点才能形成多数派，生产中通常为每个主节点配置至少一个从节点。

## 哈希槽与重定向

每个键通过 `CRC16(key) mod 16384` 决定归属槽位；客户端访问错误节点时收到 `MOVED` 重定向，
槽迁移过程中则可能收到 `ASK` 重定向。集群节点间用 gossip 协议传播槽位归属与故障状态。
`MOVED` 表示槽已永久迁移，客户端应更新本地槽位映射表后重试；`ASK` 表示仅本次请求应到目标节点，
客户端的槽位映射表此时不应更新，否则会造成映射抖动。
如果在迁移过程中大量键同时被访问，`ASK` 重定向会显著增加往返次数，因此迁移应安排在低峰期。
运维上可用 `CLUSTER SETSLOT` 与 `MIGRATE` 手动控制迁移，或借助 redis-cli --cluster reshard 自动化。

## 故障转移

主节点被多数派判定为下线后，其从节点发起选举，获得多数主节点投票后晋升为新主。
`cluster-node-timeout` 控制主观下线的判定阈值，过小会导致网络抖动时频繁切换。
主观下线（PFAIL）是单节点视角的判断，当多数主节点都报告某节点 PFAIL 时才升级为客观下线（FAIL）。
从节点晋升后，集群会自动更新槽位归属并广播新的配置纪元（config epoch），冲突时以纪元较大者为准。
若某槽位没有任何可用主节点且 `cluster-require-full-coverage` 为 yes，整个集群会拒绝写入。

## 一致性取舍

Redis Cluster 不保证强一致：主从复制是异步的，主节点在故障转移前已确认但尚未复制的写入会丢失。
它提供的是可用性优先的最终一致模型，适合缓存与可容忍少量丢失的场景。
`WAIT` 命令可以阻塞等待指定数量的副本确认，但只提供尽力而为的同步，无法构成真正的共识协议。
对账与幂等设计因此成为使用 Cluster 的必备实践：写入方应能安全重放，读取方应容忍短暂陈旧。

## 客户端要点

生产客户端需要维护槽位到节点的映射表，在重定向时刷新映射，并在拓扑变更时重新发现节点。
连接池应按节点维度拆分，避免单点连接成为瓶颈。
批量操作（如 `MGET`）在跨槽时不可用，必须按槽分组或改用 hash tag（`{user}:1`）把相关键绑定到同一槽。
`CLUSTER SLOTS` / `CLUSTER SHARDS` 是刷新拓扑的推荐命令，后者在新版本中取代前者。
